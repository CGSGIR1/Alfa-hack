## Новая подготовка новостей

Основной запрос подготовки новости дополнен `event_identity` версии `news-event-identity-1.0`:

- главный тезис и тип материала: одно событие, обзор или неопределённо;
- участники, действие, конкретный предмет и стадия;
- дата события с её ролью и период;
- существенные показатели с единицами, периодами и точными цитатами;
- идентификаторы исходных блоков, подтверждающие цитаты и ограничения.

Полная инструкция — `src/news_prep/event_identity.py`, а также в конце `company-news-analytics/prompts/news_json.md`. Версия основного запроса повышена до `news-two-views-1.0/p3-event-identity-v1`.

Отдельного LLM-запроса на сравнение каждой пары не требуется. Модель добавляет признаки в уже выполняющуюся подготовку статьи. Проверка приложения отбрасывает неподтверждённые цитаты, числа и даты; исходная статья при этом остаётся доступной.

Статусы признаков: `missing`, `partial`, `identified`, `invalid`. Наличие точных цитат не равно семантической проверке всех полей: `semantic_support_verified=false` сохраняется явно. Обзор нескольких событий не признаётся одной перепечаткой.

Функция `compare_event_features` в `src/integration/events.py` объясняет кандидатные связи по этим признакам. Различия стадии, периода и показателей отмечаются как возможное обновление. Автоматическое скрытие по новым признакам не включено: `suppress=false`. Действующие проверки URL, парсерных событий и официальных курсов сохранены.

Проверить конкретную пару из базы без LLM:

```powershell
.\.venv\Scripts\python.exe -B app.py compare-events --left ID_ПЕРВОЙ_НОВОСТИ --right ID_ВТОРОЙ_НОВОСТИ
```

При неполных признаках команда возвращает `insufficient_evidence`; она не объявляет статью дубликатом по одному похожему заголовку.

## Старые JSON и база

Старые JSON продолжают загружаться. Новые сведения хранятся в таблице `news_event_identities`, привязанной к ID новости и её версии. Отсутствующие признаки регистрируются как `missing`. Добавление только `event_identity` сохраняет `news.input_hash`, существующие векторы и оплаченные проверки компании — оно не должно запускать весь конвейер повторно.

Сначала посмотреть, какие старые новости можно дополнить:

```powershell
.\.venv\Scripts\python.exe -B app.py enrich-events --limit 10
```

Команда выше ничего не отправляет в LLM. По умолчанию выбираются последние семь дней, статьи с исходными блоками и отсутствующими признаками.

Дополнить выбранные новости через API:

```powershell
.\.venv\Scripts\python.exe -B app.py enrich-events --limit 10 --apply
```

Для одной новости добавьте `--news-id ID`. Для архива всех дат — `--all-dates`. Каждый старый материал требует отдельного короткого запроса извлечения. При ошибке API обработка останавливает дальнейшие платные запросы этой команды. Новости без исходных блоков пропускаются: пересказ не выдаётся за оригинал.

Команда `enrich-events` сохраняет дополненные копии в `runtime/news-event-enriched`, не перезаписывая первоначальные файлы. Материал с частичными признаками автоматически повторно не оплачивается этой командой.

Для всего существующего архива добавлена команда с сохранением прогресса:

```powershell
.\.venv\Scripts\python.exe -B app.py backfill-events --all-dates
.\.venv\Scripts\python.exe -B app.py backfill-events --all-dates --workers 8 --apply
```

Первая команда показывает план. Вторая обращается к API для новостей с отсутствующими признаками. Число запросов одновременно ограничено `--workers` (1–8), количество документов — `--limit` (по умолчанию 1000). При повторном запуске уже дополненные новости пропускаются. Для осознанной повторной обработки неполных признаков есть `--include-partial`, для конкретной новости — `--news-id ID`.

Этот массовый вариант обновляет только поле `event_identity` в основной базе и существующих JSON, если содержимое файла совпадает с хранимой версией. Исходные абзацы, фрагменты, тексты для эмбеддинга, векторы и история обработок не меняются. Перед запуском создаются одна полная копия базы и архив исходных JSON. Копии дополненных документов также сохраняются в `runtime/news-event-enriched`.

В `runtime/event-backfill/<дата запуска>/` находятся `progress.json`, журнал по каждой статье `articles.jsonl`, исходные ответы модели, список исходных путей и резервный ZIP. При ошибке API новые запросы больше не отправляются; уже выполняющиеся завершаются и сохраняются. При перезапуске удачные документы повторно не оплачиваются. Повторный импорт старой копии без признаков сохраняет уже извлечённые признаки той же версии текста.

Локальная проверка результата без обращения к API:

```powershell
.\.venv\Scripts\python.exe -B tools/audit_event_archive.py --output runtime/event-backfill/audit.json
```

`partial` не означает испорченную или удалённую новость: например, точная дата события в публикации может отсутствовать. Такие документы сохраняют известные признаки и ограничения; их нельзя автоматически объединять только на основании общности темы. `identified` означает прохождение механических проверок структуры и цитат, а не независимую проверку истинности всех утверждений модели.

## Агенты отчёта

В `config.json` установлен `pipeline.report_mode="deep"`:

1. Два мнения о применимости с проверкой каждого ответа; при расхождении — арбитр.
2. Отдельный анализ принятой новости с доступом к её исходному тексту, дополнительным кандидатам аналитики и истории показателей из основной базы.
3. Короткая сводка, устранение повторения независимых рисков, проверка и доработка проблемных частей.
4. Оценка силы влияния по пяти факторам. Баллы задаёт модель с обоснованиями, итоговый уровень считает код. Это качественная шкала, не вероятность и не численный прогноз убытка.

Новый документ — `company-report-2.0`; устойчивый формат подтверждения обработанного пакета остаётся `company-analysis-report-1.1`. Сайт поддерживает оба поколения отчётов. Основания оценки скрыты в раскрывающемся разделе. Полные источники и дополнительная аналитика сохраняются для проверки.

Поддержка `report-generation-input-1.1`, точных цитат и специальной отметки материалов организаторов сохранена. Упоминание издателя «Альфа-Банк» само по себе не создаёт такую отметку. Дополнительные материалы агента сохраняются в `evidence_catalog`, поэтому после перезапуска ссылки не теряются.

В основной базе добавлена таблица `indicators`; обновлённый сборщик показателей работает с ней через отдельный контекст, не создавая поверх неё таблицы старого прототипа. Обновить показатели отдельно:

```powershell
.\.venv\Scripts\python.exe -B app.py collect-indicators --days 400
```

Отчёт использует доступные сохранённые показатели, отсутствие данных не заменяется вымышленными значениями. Дополнительная история не возвращает точки позже даты отчёта. Для исторического отчёта текущий снимок показателей не подставляется.

## Настройки и стоимость

- `LLM_MODEL_REPORT`, иначе `LLM_MODEL_MAIN` — основная модель.
- `LLM_MODEL_SECOND`, иначе модель второго мнения из архива `z-ai/glm-5.3-flash`.
- `LLM_MODEL_CRITIC`, иначе модель второго мнения — критик.
- `pipeline.critic` — включение критика.
- `pipeline.report_budget_rub=20.0` — ориентир бюджетного предохранителя из обновления: он пропускает необязательные стадии по оценке затрат. Это не жёсткий предел списания API; отдельный уже отправленный запрос может превысить оценку.
- `pipeline.report_mode="standard"` — совместимый прежний конвейер.

Короткий итоговый текст не гарантирует меньшего расхода: новая схема использует несколько мнений и проверок. Реальные расходы журналируются. Параллельные стадии учитывают токены по своим потокам, без двойного сложения расхода в трассировке.
